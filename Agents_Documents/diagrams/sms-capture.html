happy path rejection / quarantine infra / plumbing

1 · Happy path — one M-PESA SMS to a stored capture

The Consent API surfaces a single SMS only after the user taps "Allow" on the system dialog. Raw text never leaves the device until the strict TS parser accepts it, and even then only a hashed payer id (no raw phone, no message text) is sent. The backend dedupes by client_event_id and by receipt, merges processor-side records, and emits an outbox event — but quarantines unverified rows so they never reach revenue totals.

2 · Frontend function map

The native module is Android-only and optional: every function degrades to a no-op on iOS/web so the rest of the app builds. handleIncomingSms is the single facade — the only place a parsed SMS becomes a queued ingest item.

Flowchart · backend ingest pipeline

Backend ingest — validation, merge, outbox

3 · Backend ingest pipeline

Each item runs in its own transaction so one bad row never fails the batch. DecideMerge is a pure function (no DB) reused by the Pesapal/Daraja paths. Device-reported and disputed rows are quarantined by VerifiedScope() and never feed revenue, analytics or tax.

Captured payment states

4 · CapturedPayment state machine

Trust only goes up: a processor-side record (Pesapal/Daraja) upgrades a device-reported row to verified, never the reverse. A receipt collision with a different amount marks both rows disputed for review.

Device registration (first capture)

5 · Device registration

A device id is minted once per install via POST /devices and cached in SecureStore. Unknown devices are rejected with device_unknown, so a replayed client_event_id from a foreign device cannot create a capture.
